### 2. Event-Driven vs. Cycle-Accurate {#event-vs-cycle}

#### 2.1 Cycle-Accurate仿真（传统方法）

**原理：** 每个时钟周期都检查系统状态

```python
# 逐周期仿真
for cycle in range(0, 10000):
    # 周期0: 检查所有资源 → 空闲
    # 周期1: 检查所有资源 → 空闲
    # ...
    # 周期999: 检查所有资源 → 空闲
    # 周期1000: 检查所有资源 → 传输开始！
    # 周期1001: 检查所有资源 → 传输中
    # ...
    # 周期2000: 检查所有资源 → 传输完成！
    
    update_all_components()
    check_all_conditions()

# 结果: 检查了10000次，但只有1000次有意义
```

**问题：**
- ❌ **慢**: 大量时间浪费在检查空闲周期
- ❌ **不可扩展**: 仿真1M周期需要1M次迭代
- ❌ **复杂**: 需要维护每个周期的详细状态

**时间复杂度：** O(总周期数)

---

#### 2.2 Event-Driven仿真（推荐方法）

**原理：** 只处理有意义的事件，跳过空闲周期

```python
# Event-driven仿真
event_queue = PriorityQueue()  # 按时间排序
current_time = 0

# 只有2个event
event_queue.add(Event(time=1000, type=START))
event_queue.add(Event(time=2000, type=COMPLETE))

while not event_queue.empty():
    event = event_queue.pop()
    current_time = event.time  # 直接跳到event时间
    handle_event(event)

# 结果: 只迭代了2次！
# 时间从0→1000→2000，跳过了所有空闲周期
```

**优势：**
- ✅ **快**: 100-1000倍加速
- ✅ **可扩展**: 只与event数量相关，不与总周期数相关
- ✅ **简洁**: 只需关注有意义的状态变化

**时间复杂度：** O(event数量 × log(event数量))

---

#### 2.3 对比示例

**场景：** 仿真4个传输，每个100周期，间隔1000周期

```
Timeline:
0    100  1100 1200  2200 2300  3300 3400
|====T1==|    |==T2==|    |==T3==|    |==T4==|

总周期: 3400
有意义的周期: 400 (4 × 100)
空闲周期: 3000
```

**Cycle-Accurate:**
```
迭代次数: 3400次
有用的迭代: 400次
浪费率: 88%
执行时间: 3.4秒 (假设1ms/cycle)
```

**Event-Driven:**
```
Event数量: 8个 (4个START + 4个COMPLETE)
迭代次数: 8次
浪费率: 0%
执行时间: 8ms (假设1ms/event)
加速比: 425倍！
```

---

#### 2.4 何时使用哪种方法

| 场景 | 推荐方法 | 原因 |
|------|----------|------|
| **稀疏活动** (大量空闲周期) | Event-Driven ✓ | 跳过空闲时间 |
| **密集活动** (每周期都有事) | Cycle-Accurate | Event开销大 |
| **性能估算** | Event-Driven ✓ | 快速评估 |
| **功能验证** | Cycle-Accurate | 需要逐周期正确性 |
| **早期设计探索** | Event-Driven ✓ | 快速迭代 |
| **详细时序分析** | Cycle-Accurate | 需要周期级精度 |
| **大规模仿真** (>1M周期) | Event-Driven ✓ | 可扩展性 |
| **小规模仿真** (<1K周期) | 两者皆可 | 差异不大 |

**经验法则：**
```
使用Event-Driven，如果：
1. 空闲时间 > 50%
2. 仿真周期 > 10K
3. 需要快速迭代
4. 可接受±5%误差

否则使用Cycle-Accurate
```

### 3. 核心建模概念 {#core-concepts}

#### 3.1 三个基本要素

```
┌─────────────────────────────────────────┐
│     硬件性能建模的三个基本要素           │
└─────────────────────────────────────────┘

1. Resource (资源)
   └─ 系统中需要竞争的组件
      例: 处理器、内存端口、总线、缓冲区
      
2. Operation (操作)
   └─ 需要执行的任务
      例: 数据传输、计算任务、内存访问
      
3. Event (事件)
   └─ 系统状态变化的时间点
      例: 操作开始、操作完成、资源释放
```

#### 3.2 五个核心机制

```
┌──────────────────────────────────────────────┐
│    必须建模的五个核心机制                     │
└──────────────────────────────────────────────┘

机制1: Event Queue (事件队列)
├─ 作用: 按时间顺序管理所有事件
├─ 实现: 优先队列 (最小堆)
└─ 关键: 自动按时间排序

机制2: Resource Contention (资源竞争)
├─ 作用: 处理多个操作竞争同一资源
├─ 实现: 资源状态追踪 (busy_until时间)
└─ 关键: 串行化或带宽共享

机制3: Dependency Tracking (依赖追踪)
├─ 作用: 确保操作按正确顺序执行
├─ 实现: 依赖图 + 完成集合
└─ 关键: 检查所有依赖是否满足

机制4: Notify Mechanism (通知机制)
├─ 作用: 依赖满足时唤醒等待的操作
├─ 实现: 反向依赖图 + 主动通知
└─ 关键: 避免轮询，高效触发

机制5: Parallel Execution (并行执行)
├─ 作用: 支持多个操作同时运行
├─ 实现: 多资源独立追踪
└─ 关键: 正确处理资源竞争
```

### 4. 建模决策清单 {#design-decisions}

在开始建模前，必须回答这些问题：

#### 4.1 关键决策表

| 决策项 | 问题 | 选项 | 如何选择 |
|--------|------|------|----------|
| **Q1** | 用几个event queue? | ① 1个全局<br>② 多个分布式<br>③ 混合 | < 100组件 → ①<br>> 1000组件 → ②<br>中等 → ③ |
| **Q2** | Event粒度? | ① 粗粒度(2种)<br>② 细粒度(4-6种) | 快速估算 → ①<br>精确建模 → ② |
| **Q3** | 资源竞争如何处理? | ① 串行化<br>② 带宽共享<br>③ 容量限制 | 互斥资源 → ①<br>可共享 → ②<br>有限并发 → ③ |
| **Q4** | 依赖如何表示? | ① 显式图<br>② 隐式时间<br>③ 混合 | 复杂依赖 → ①<br>简单顺序 → ②<br>两者都有 → ③ |
| **Q5** | 如何通知依赖? | ① 轮询<br>② 主动notify | 简单 → ①<br>高效 → ② ✓ |
| **Q6** | 调度策略? | ① 贪心(ASAP)<br>② 优先级<br>③ 优化算法 | 吞吐量 → ①<br>多优先级 → ②<br>特殊需求 → ③ |
| **Q7** | 时间如何推进? | ① 事件驱动<br>② 固定步长 | 稀疏活动 → ①<br>密集活动 → ② |
| **Q8** | 统计如何收集? | ① 实时增量<br>② 事后分析 | 简单指标 → ①<br>复杂分析 → ② |

#### 4.2 决策树：Event Queue数量

```
START HERE ↓

┌─ 系统有多少个组件？
│
├─ < 10个组件
│  └─→ 使用 1个全局队列 ✓
│      理由: 简单、够用、易调试
│
├─ 10-100个组件
│  │
│  ├─ 组件之间紧耦合？(共享资源、有依赖)
│  │  ├─ YES → 1个全局队列 ✓
│  │  │         理由: 需要全局时序
│  │  │
│  │  └─ NO → 考虑混合方式
│  │            理由: 可以分离全局/局部事件
│  │
│  └─ 是你的第一个模型？
│     └─ YES → 1个全局队列 ✓
│               理由: 从简单开始
│
└─ > 100个组件
   │
   ├─ 组件之间松耦合？(独立执行)
   │  ├─ YES → 多个队列
   │  │         理由: 可扩展、可并行
   │  │
   │  └─ NO → 1个全局队列 ✓
   │            理由: 需要协调
   │
   └─ 需要并行仿真？(多CPU)
      ├─ YES → 多个队列
      │         理由: 可并行处理
      │
      └─ NO → 1个全局队列 ✓
                理由: 简单高效

结论: 90%的情况应该用 1个全局队列！
```

#### 4.3 推荐配置

**场景1: 你的DMA系统 (4通道)**

```
✓ Event Queue: 1个全局队列
✓ Event粒度: 细粒度(START, ISSUE, DRAIN, COMPLETE)
✓ 资源竞争: 串行化(端口互斥) + 容量限制(OB)
✓ 依赖表示: 混合(显式依赖 + 时间约束)
✓ 通知机制: 主动notify
✓ 调度策略: 贪心(ASAP)
✓ 时间推进: 事件驱动

理由: 小系统、紧耦合、需要精确建模
```

**场景2: CPU多核系统 (8核)**

```
✓ Event Queue: 1个全局队列
✓ Event粒度: 粗粒度(START, COMPLETE)
✓ 资源竞争: 带宽共享(缓存) + 串行化(总线)
✓ 依赖表示: 混合
✓ 通知机制: 主动notify
✓ 调度策略: 优先级
✓ 时间推进: 事件驱动

理由: 中等系统、有共享资源、需要优先级
```

**场景3: 大型网络 (1000路由器)**

```
✓ Event Queue: 多个队列(每路由器一个)
✓ Event粒度: 粗粒度
✓ 资源竞争: 带宽共享(链路)
✓ 依赖表示: 隐式(报文顺序)
✓ 通知机制: 轮询(松耦合系统)
✓ 调度策略: 优先级(QoS)
✓ 时间推进: 事件驱动

理由: 大系统、松耦合、需要可扩展性
```

### 5. 建模的7个步骤 {#methodology}

#### 步骤1: 理解问题

**目标：** 明确建模目标和需求

**问题清单：**
```
□ 要建模什么系统？
  - 组件有哪些？
  - 如何交互？
  - 资源有哪些？

□ 建模的目的是什么？
  - 性能估算？精度要求？
  - 瓶颈分析？
  - 设计空间探索？

□ 需要回答什么问题？
  - 吞吐量是多少？
  - 延迟有多大？
  - 资源利用率？
  - 哪里是瓶颈？

□ 可接受的误差是多少？
  - ±5%? ±10%? ±20%?
  - 影响决策即可？
```

**输出：** 需求文档

---

#### 步骤2: 选择抽象层次

**目标：** 决定建模什么、简化什么、忽略什么

**抽象决策表：**

| 方面 | 详细建模 | 简化建模 | 忽略 | 你的选择 |
|------|----------|----------|------|----------|
| **数据移动** | 逐字节追踪 | 只记录时间 | ✓ | 只记录时间 |
| **端口竞争** | 详细仲裁 | ✓ | 假设无冲突 | 详细建模 |
| **Outstanding Buffer** | 逐entry追踪 | ✓ | 无限容量 | 容量限制 |
| **依赖关系** | 完整DAG | ✓ | 假设独立 | 完整追踪 |
| **带宽变化** | 动态调整 | 固定值 | ✓ | 固定值 |
| **延迟变化** | 随机分布 | 固定值 | ✓ | 固定值 |
| **功耗** | 详细建模 | 简单估算 | ✓ | 忽略 |

**原则：**
- ✅ 对性能影响大的 → 详细建模
- ✅ 影响中等的 → 简化建模  
- ✅ 影响小的 → 忽略

**输出：** 抽象文档，列出所有假设

---

#### 步骤3: 设计架构

**目标：** 确定组件结构和接口

**架构图：**

```
┌────────────────────────────────────────────┐
│           Event-Driven Simulator           │
│  ┌──────────────────────────────────────┐  │
│  │  主仿真循环                           │  │
│  │  while event_queue不空:              │  │
│  │    event = queue.pop()               │  │
│  │    current_time = event.time         │  │
│  │    处理event                          │  │
│  │    尝试调度新操作                     │  │
│  └──────────────────────────────────────┘  │
└────────────────────────────────────────────┘
        │                    │
   ┌────▼────────┐     ┌────▼────────────┐
   │  Resource   │     │   Dependency    │
   │  Manager    │     │   Tracker       │
   │             │     │                 │
   │  - 追踪资源  │     │  - 追踪依赖     │
   │  - 检查可用  │     │  - 完成通知     │
   │  - 获取/释放 │     │  - 维护就绪队列 │
   └─────┬───────┘     └────┬────────────┘
         │                   │
   ┌─────▼───────────────────▼────┐
   │       Scheduler              │
   │  - 选择下一个操作             │
   │  - 计算开始时间               │
   │  - 处理冲突                   │
   └──────┬───────────────────────┘
          │
   ┌──────▼───────────────────────┐
   │   Performance Model          │
   │  - 计算周期数                 │
   │  - 带宽建模                   │
   │  - 延迟计算                   │
   └──────────────────────────────┘
```

**组件职责：**

1. **Simulator**: 主循环，协调各模块
2. **ResourceManager**: 资源状态管理
3. **DependencyTracker**: 依赖关系管理
4. **Scheduler**: 操作调度决策
5. **PerformanceModel**: 性能计算

**输出：** 架构设计文档

```
层次3: 系统测试 (5%测试)
├─ 测试完整workload

└─ 工具: 回归测试套件
```

**验证checklist:**

```

□ 资源最终被释放
□ 统计数据正确
□ 与已知结果对比 (±5%误差内)
```

**输出：** 测试报告

#### 步骤6: 优化

**目标：** 提升速度和精度

**优化方向：**

```
性能优化:
├─ 使用合适的数据结构
│  └─ 优先队列: O(log n)
│  └─ 哈希表: O(1)查找
│  └─ 数组: O(1)访问
│
├─ 减少不必要的计算
│  └─ 缓存频繁计算的值
```

```
2个处理器 (P0, P1)

  - 任务A: 50周期，无依赖
  - 任务B: 30周期，依赖A
  - 任务C: 30周期，依赖A
```

```
- A首先执行 (0-50)

```

- ✓ Event-driven
- ✓ 资源竞争 (内存)
- ✓ 依赖关系 (A→B, A→C, B→D, C→D)
- ✓ Notify机制 (A完成通知B和C)
- ✓ 并行执行 (B和C同时)
